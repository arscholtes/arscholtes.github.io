01Work that carries load

Liftify

A multi-tenant reputation and customer-experience platform for home-service businesses. Rails 7.2 monolith, PostgreSQL, Sidekiq, Hotwire, event-sourced domain layer. I joined in March 2026 and have been the primary engineer on its ticketing and automations subsystems since.

115pull requests merged
61klines added
13klines deleted
6months

  • An append-only history of every status and assignment change

    Support kept asking “who moved this, and when.” I added an immutable history table written from model callbacks, so the answer is a query instead of a guess — and the analytics team could report on it without touching application code.

  • A generic time trigger for the automations engine

    The rules engine could only react to things happening. It could not react to things not happening. I added an elapsed-time trigger as a first-class condition, which turned “notify me when a ticket has sat untouched for two days” from a feature request into a configuration change.

  • Custom-field conditions, built once for every rule type

    The ask was custom-field conditions on one kind of rule. Building it there would have meant building it four more times later. I pushed the condition loading down into the shared rule processor instead, so every current and future rule context got it in the same commit.

  • Location-scoped access control on the paths that leaked

    Users were scoped to their locations on the pages, but not on assign, watch, and mention. Those three paths let you reach a person you were not supposed to see. I closed them against the existing scoping concern rather than adding a fourth check.

  • Notification coalescing, then digests

    A bulk import could fire several hundred instant notifications at one person. I made every instant notification type coalescable, then added scheduled digest delivery on top of the same mechanism.

  • A ranking query that got slower every month

    Contact ranking aggregated the full touchpoint history — a table that only grows. Bounding it to a rolling twelve-month window cut the work without changing a single result any user would notice.

02Tools I built to ship faster

The machine around the work

The throughput above is not heroics. It is tooling. Most of what I have built for myself in the last year is infrastructure for working with coding agents — giving them narrow jobs, hard boundaries, and somewhere to hand work off.

FPS

Five agent sessions, five jobs, five lists of things they may not do

Python1.5k LOCPublic

One coding agent asked to do everything does everything badly. FPS splits the work across five concurrent sessions with fixed charters and enforced boundaries: one builds and stops at a draft, one holds the day’s state, one takes existing work through review to merged, one watches services, one turns finished work into explanations.

forgebuilds — never lands pilotorients — never codes shepherdlands — never starts wardenwatches — never fixes mentorteaches — never flatters

The constraint is the whole idea. A session that cannot land its own work has to write a handoff good enough for another session to land it — which is the same document a human reviewer needed all along.

Five code-review agents

Reviewers with one question each

Private

A general “review this” prompt returns nitpicks. Each of these asks exactly one thing and produces evidence for its answer: does it break, was it built at the right level, does something like it already exist, will the query survive production scale, will anyone maintain it.

The reuse gate is the one that earns its keep. Before it, my most common review comment was some version of we already have this.

Standup planner

A deterministic core with a language model on the outside

Python4.7k LOCPrivate

Pulls the open cycle, my pull requests, and my calendar, then ranks the day and lays out focus blocks. The ranking is plain tested Python, not a prompt — a model that reorders your priorities differently every morning is worse than no planner at all. The model gathers and narrates; it does not decide.

Writes blocks to the calendar only after I say yes.
